# hmp-core

`hmp-core` is the persistent server-side spine of the HMP Foundations stack. It owns accounts,
identity links, character slots, scoped groups and JSON metadata. Other resources consume these
APIs instead of creating competing player tables.

It requires `hmp-mysql` and `hmp-lib`. On startup it applies its versioned schema migrations before
accepting player sessions.

## Identity model

The account ID generated by `hmp-core` is the stable ownership key. The current HogwartsMP runtime
only exposes client-announced Steam, Discord and hardware identifiers. Accordingly, the built-in
fallback stores them as `client-steam`, `client-discord` or `client-hardware` with trust level
`asserted`. They must not be treated as proof for sensitive authorization.

A client announces only the identifiers it detected on that launch, so Steam or Discord can be missing
from one session to the next. Every announced identifier is linked to the account, and a later session
is matched through any of them, ranked by `identityOrder`. An identifier already linked to another
account is never moved; the server logs a warning naming both account IDs instead. If a new
higher-ranked identifier arrives with one that matches an account that already holds a different
identifier of that kind, as with two Steam users on one machine, the player gets a separate account.
Remove `hardwareId` from `identityOrder` to stop matching and linking hardware IDs.

A later MafiaHub authentication resource can register a higher-priority server-validated provider:

```js
const Core = Imports.get("hmp-core");

const unregister = Core.identity.register({
    name: "mafiahub-auth",
    resource: "hmp-auth",
    priority: 100,
    trust: "verified",
    async resolve(player) {
        const identity = await validateMafiaHubSession(player);
        return identity && { provider: "mafiahub", subject: identity.id, trust: "verified" };
    },
});
```

After validating ownership, `Core.accounts.linkIdentity(accountId, principal)` links that verified
principal to the existing internal account. An identity already owned by another account is rejected,
never silently transferred.

## Join tickets

A `hogwartsmp://host:port?ticket=…` link, such as a Join button on your website, starts the game and
joins with that `ticket`. Every other identifier is whatever the client reports, but a client cannot make
up a ticket your site issued and checks. `hmp-core` asks the resources that register a ticket redeemer
about it before the player takes a slot:

```js
Core.tickets.register({
    name: "website",
    resource: "my-site",
    async redeem({ ticket, hardwareId }) {
        return site.redeem(ticket, hardwareId); // e.g. { accountId } when it is good, else null
    },
});
```

Redeemers are asked from the highest `priority` down; the first truthy result accepts the ticket, and a
throw counts as a refusal. `Core.tickets.get(player)` then returns `{ redeemer, result, repeat }` from
`playerConnect` until the player leaves, so an identity provider registered at a higher priority can turn
the result into a verified principal. It is matched to the player by nickname, hardware ID and address,
and is null when no ticket was accepted.

- **One join can present a ticket twice**: when the game restarts to apply the server's mods, and on the
  join dialog's Try again. A ticket accepted once is accepted again from the same hardware ID and
  address for `tickets.repeatSeconds` (120 by default) without asking the redeemers, so they can spend it
  on first use.
- **A join from the server list carries none**: its ticket is an empty string, and no redeemer is asked.
- **It is not encrypted on the wire**, so keep tickets short-lived and single-use. `hmp-core` never logs
  one.

With `tickets.required: true`, a join no redeemer accepted is turned away with `tickets.rejectMessage`
before it takes a slot. It is off by default, so tickets are only read.

Join tickets need HogwartsMP `1.11` or newer, whose clients pass their link's ticket on. On an older host
every ticket is empty, so redeemers are never asked, and `tickets.required` is ignored with a warning
rather than turning everyone away.

## Exports

- `status()` reports startup state and session/provider counts.
- `identity` registers and resolves identity providers.
- `accounts` looks up accounts and links additional identities.
- `sessions` exposes connected, initialized account sessions.
- `characters` lists, creates, selects, unloads and soft-deletes character records.
- `groups` manages account/character roles and calculates effective membership.
- `metadata` stores JSON values at account or character scope.
- `tickets` registers join ticket redeemers and reads the ticket a player joined with.

All mutating APIs return promises. See `types.d.ts` for the full contract.

Character records deliberately contain only identity and slot lifecycle fields. Appearance, location,
inventory and other systems should own their own versioned tables keyed by `character.id`.
`hmp-characters` provides the multicharacter UI and appearance handoff using this API.

## Configuration

Create `data/hmp-core.json` in the server working directory when overrides are needed:

```json
{
  "maxCharacters": 4,
  "autoSelectSingleCharacter": false,
  "duplicateSession": "reject-new",
  "duplicateSessionGroup": "admin",
  "duplicateSessionMinimumGrade": 1,
  "kickDuplicateSession": false,
  "identityOrder": ["steamId", "discordId", "hardwareId"],
  "tickets": {
    "required": false,
    "rejectMessage": "Join this server from its website.",
    "repeatSeconds": 120
  }
}
```

Set `duplicateSession` to `allow-group` to permit simultaneous sessions only for accounts whose
configured account-level group meets `duplicateSessionMinimumGrade`. Sessions still select
characters independently, and one character cannot be active in two sessions at once.

`HMP_CORE_CONFIG`, `HMP_CORE_MAX_CHARACTERS`, `HMP_CORE_AUTO_SELECT_SINGLE`,
`HMP_CORE_DUPLICATE_SESSION`, `HMP_CORE_DUPLICATE_GROUP`, `HMP_CORE_DUPLICATE_MIN_GRADE`,
`HMP_CORE_KICK_DUPLICATE`, `HMP_CORE_IDENTITY_ORDER` and `HMP_CORE_REQUIRE_TICKET` provide environment
overrides.

## Lifecycle events

The resource emits `hmp:session:ready`, `hmp:session:ended`, `hmp:character:created`,
`hmp:character:loading`, `hmp:character:loaded`, `hmp:character:unloading`,
`hmp:character:unloaded`, `hmp:character:deleted`, `hmp:groups:changed` and
`hmp:metadata:changed` for other server resources.

A session loads one character at a time. `characters.select` of another character while one is loading
rejects with `HMP_CORE_CHARACTER_LOADING`; a second select of the same character shares the first one's
result. If the player disconnects during a select, it rejects with `HMP_CORE_SESSION_MISSING` and raises
nothing after `hmp:session:ended`. A character whose load was still running keeps its claim until the
`hmp:character:loading` handlers return, or for at most 30 seconds, so no other session loads it alongside
them.
